# dialekt.ai — Legal Brief for Privacy Policy & Terms of Service

**Назначение документа:** входной материал для юриста, который будет составлять Privacy Policy и Terms of Service для дialekt.ai. Ниже — полная карта потоков данных, целей обработки, retention-политик, sub-processors и юридических привязок.

**Юрисдикции для покрытия:**
1. **РК — Закон «О персональных данных и их защите» №94-V** (с изменениями от 18.01.2026 — ужесточение для cross-border transfer)
2. **EU — GDPR** (если хотя бы один пилот в EU; продукт скачиваемый, доступен глобально)
3. **РФ — №152-ФЗ** (если ожидаются пилоты из РФ)

---

## 1. Структура продукта (что юристу нужно понять до текста)

dialekt.ai — настольное приложение (Tauri/Electron-class) с двумя слоями:

- **Локальный слой (desktop app)** — устанавливается на компьютер пользователя. Локальный backend на FastAPI слушает на `localhost:8765`. Все промпты, ответы LLM, история чатов, кэш — на машине пользователя в `~/.dialekt/`. Никакой телеметрии по умолчанию.
- **Облачный слой (`dialekt-cloud`)** — FastAPI + PostgreSQL, развёрнут на инфраструктуре Контролёра (КЗ, Cloudflare-tunneled). Хранит: тенанты (компании-клиенты), лицензионные ключи, пользователей-владельцев, инвойсы. Минимальные данные.

**Ключевая позиционная формулировка:** «Local-first AI agent. Your prompts, code, and files never leave your machine.» Это маркетинг-обещание, и оно ДОЛЖНО юридически держаться. Privacy Policy не должна противоречить.

## 3. Категории обрабатываемых ПДн

### 3.1 Регистрационные данные (cloud)

Собираются при регистрации на лендинге через форму signup:

| Поле | Тип | Обязательное | Цель обработки |
|---|---|---|---|
| `email` | email-адрес | да | идентификация аккаунта, отправка лицензии, восстановление |
| `full_name` | ФИО | да | персонализация коммуникации, инвойсы |
| `intended_use` | свободный текст | да | сегментация пилотов, квалификация лидов |
| `country` | ISO 3166-1 страна | да | юрисдикционная сегментация, sub-processor routing |
| `signup_source` | UTM source (опц) | нет | маркетинг-аналитика |

**Дополнительно (после активации в desktop first-run wizard):**
- `company_name` — название компании
- `role_in_company` — должность

**Технические данные при signup:**
- IP-адрес (для rate-limit, anti-abuse) — хранится 30 дней
- User-agent (анти-абьюз)

### 3.2 Платёжные данные (cloud)

- **Что:** название плательщика, БИН/ИНН (для KZ-инвойсов), банковские реквизиты (если SEPA/SWIFT для EU-клиентов)
- **Где хранится:** в `invoices` таблице PG. PDF-инвойсы — на диске Контролёра.
- **Платёжный процессор:** **в текущей версии нет онлайн-платежей** — оплата вне продукта (счёт-фактура, банковский перевод). Если в будущем будет добавлен Stripe/Robokassa/Kaspi Pay — этот пункт надо переписать.

### 3.3 Локальные данные (на машине пользователя — НЕ в облаке)

Перечислить в Privacy Policy для прозрачности, **но указать что Контролёр к ним не имеет доступа**:

- Промпты пользователя к LLM
- Ответы LLM (Ollama локально или через cloud LLM-провайдеров — см. 3.4)
- История чатов (`~/.dialekt/dialekt.db`)
- Файлы / содержимое директорий, к которым агент имеет доступ
- API-ключи cloud LLM-провайдеров (хранятся в OS keychain, не отправляются на dialekt-cloud)

**Юридически важно:** dialekt не является обработчиком этих данных. Они никогда не покидают устройство пользователя по умолчанию.

### 3.4 Cloud LLM provider routing (опциональный data flow)

Если пользователь добавляет cloud LLM-провайдера (Anthropic / OpenAI / Google Gemini / AWS Bedrock / NVIDIA NIM / Mistral / DeepSeek / xAI / Cohere / Groq / Together / Fireworks / Perplexity / OpenRouter / Cerebras / Replicate / Azure / Vertex AI):

- **Промпты пользователя отправляются напрямую с его машины** к API провайдера (peer-to-peer; через dialekt-cloud НЕ проходят)
- Провайдер становится **самостоятельным контролёром / обработчиком** этих данных
- Privacy Policy ДОЛЖНА перечислить всех 18 провайдеров как «third parties whose terms apply when the user enables them»
- Каждому провайдеру в приложении показывается отдельная privacy-плашка (это уже реализовано в UI)

### 3.5 Логи / телеметрия

**Облачный слой (dialekt-cloud):**
- Access logs (FastAPI/uvicorn): IP, путь, статус, user-agent, timestamp
- Application logs: ошибки signup, validate-license, invite — БЕЗ содержимого промптов
- Retention: 90 дней, потом ротация

**Локальный слой:** логи хранятся локально (`~/.dialekt/logs/`), не отправляются.

## 7. Cross-border transfer (КЛЮЧЕВОЕ для KZ ПДн §16)

С 18.01.2026 РК ужесточил требования: трансграничная передача ПД из РК в страну, которая НЕ обеспечивает «адекватный уровень защиты», требует:
- отдельного **письменного согласия** субъекта ПД
- или иного основания (договор с типовыми условиями, аналог GDPR SCC)

**Адекватные страны:** ЕС, Швейцария, Великобритания, ЕАЭС-страны (РФ, Беларусь, Армения, Кыргызстан) — нужно сверить с актуальным списком РК на дату подписания политики.

**Неадекватные:** США (где сидят OpenAI, Anthropic, Google по умолчанию, AWS), Китай (DeepSeek), Израиль/Великобритания (xAI region depending), и т.д.

**Юридические следствия для Privacy:**
1. Раздел «Трансграничная передача» обязателен
2. Перед использованием cloud LLM-провайдеров пользователь должен дать **отдельное согласие** на cross-border transfer (мы покажем это в UI как чекбокс «I consent to cross-border transfer of my prompts to <provider>»)
3. Если есть регулируемые KZ-клиенты (банки, госорганы, медицина) — для них нужен `regulated_mode: true` (уже есть в settings), который **полностью отключает cloud-провайдеров**

## 9. Технические и организационные меры (TOM)

Юрист попросит описать. Краткая правда:

- **Encryption at rest:** Postgres encrypted FS (Cloudflare/server-level), inventories `dialekt_cloud` БД. Локальные API-ключи cloud-провайдеров — в OS keychain (Linux: GNOME Keyring / KDE Wallet, macOS: Keychain, Windows: Credential Manager). Fallback — XOR + scrypt-derived ключ.
- **Encryption in transit:** все API-эндпоинты требуют HTTPS (Cloudflare-tunneled). SMTP — STARTTLS на 587 / implicit TLS на 465.
- **Access control:** роль-based в admin (роль `admin` через JWT), role-based в tenants (`owner`, `user`).
- **Audit log:** `founder_admin_log` фиксирует все админские действия (создание тенантов, продление, выдачу).
- **Backups:** ежедневные снапшоты PG, 7-дневная ротация.
- **2FA для admin:** [уточнить — есть ли сейчас? Если нет — план внедрения]
